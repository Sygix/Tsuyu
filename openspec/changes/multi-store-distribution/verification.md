# Multi-store distribution verification

## Status

11 implementation tasks are verified: 2.1–2.4, 3.1, 3.3, 3.5, 4.1, 4.3, 4.5 and 4.6. Implemented but not yet proven: 4.4 (release workflow, exercised locally with throwaway keys, not run on GitHub). Open: 2.5 (Compose navigation tests per variant), 3.2, 3.4 and 3.6 (runtime transitions), 4.2 (split delivery), the reproducibility, submission and community tasks of groups 5–7.

## Results

- **Variants.** `./gradlew test lint assembleRelease bundleStoreRelease` passes for both variants: app 200 tests (standalone) and 170 (store), server 97 and 89. The store server answers `installUpdate` from the manager with `UNSUPPORTED` after closing the descriptor and still rejects other callers.
- **Store payload.** Updater class names are kept by R8 (`-keepnames`) so the dex check sees them. `scripts/check-artifacts.sh` passes on the release APKs and store bundle: same package, versionName and versionCode as `version.properties`; the standalone manifest declares the updater activity and its code contains the updater and the server installer; the store APK and bundle contain neither, and the bundle's base module contains the server entry point. Swapping the arguments, passing the standalone APK as the store one, or a store APK carrying the standalone code, makes the check fail.
- **Strings.** The string keys and texts of the five languages are unchanged: 36 updater-only strings moved to the standalone source set, none added. The two Home notice strings stay shared because Home renders the notice surfaces in both variants; the store build never fills them.
- **Cleanup and replacement rule.** Unit tests cover the store cleanup (both work names cancelled once and awaited, a standalone write re-arming it, managed cache emptied, a symbolic link to a file outside the cache left alone, updater state reset while the recorded versionCode is kept, corrupt state replaced, a failed or timed-out cancellation retried) and the standalone rule (out-of-band replacement turns automatic updating off and drops the offer, result and pending notice before any work, updater-installed and unchanged versions keep it, a missing record is the first observation, an unreadable or timed-out record skips automatic work for the process while manual checks still run).
- **Artifact names.** Gradle writes `tsuyu-X.Y.Z-<variant>-release[-unsigned].apk` and `tsuyu-X.Y.Z-store-release.aab`; releases publish `tsuyu-X.Y.Z-standalone.apk`, `tsuyu.apk` (same bytes, for updaters before 0.4), `tsuyu-X.Y.Z-store.apk`, `tsuyu-X.Y.Z-store.aab` and `SHA256SUMS`. The updater prefers the versioned standalone name and falls back to `tsuyu.apk` (`ReleasesTest`).
- **Version source.** Gradle reads `version.properties`; a wrong versionCode fails with "versionCode 300298 in version.properties does not match versionName 0.3.2 (expected 300299)" and a missing key with "versionCode missing or malformed".
- **Signing.** Without signing inputs the release APKs are produced unsigned and `apksigner verify` rejects them. With two throwaway keys, the release workflow's commands confirmed both APKs signed by the release key and the bundle by the upload key. The workflow compares both keystores and artifacts with fingerprints held outside the secrets: the committed release certificate (taken from the published 0.3.2 APK) and the `TSUYU_UPLOAD_CERT_SHA256` variable. No dependency-metadata file is present in the bundle.
- **Native code.** Both store artifacts package two AndroidX libraries (`libandroidx.graphics.path.so`, `libdatastore_shared_counter.so`) for arm64-v8a, armeabi-v7a, x86 and x86_64; every LOAD segment is 16 KB aligned and `zipalign -c -P 16` succeeds.
